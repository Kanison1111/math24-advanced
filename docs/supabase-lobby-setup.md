# Math 24 Advanced — Supabase Lobby Backend (ระยะเตรียมระบบจริง)

## สิ่งที่เพิ่มในระยะนี้

เพิ่ม migration `supabase/migrations/202611150001_lobby_foundation.sql` เพื่อรองรับ:
- ห้องแข่งขันที่มีชื่อ รหัส 6 หลัก โหมด ความยาก จำนวนข้อ เวลา และรูปแบบ Ranking
- ผู้เล่นในห้อง สถานะพร้อม และสิทธิ์เจ้าของห้อง
- RPC สำหรับสร้างห้อง, เข้าห้อง, กดพร้อม, เริ่มห้อง และออกจากห้อง
- RLS ให้ผู้เล่นอ่านได้เฉพาะห้องที่ตนเป็นสมาชิก; ห้ามเขียนตารางโดยตรง
- จำกัดการลองรหัสห้อง 5 ครั้งต่อ 10 นาทีต่อบัญชี และจำกัด 50 คนต่อห้อง

**ยังไม่มีการแข่งขันออนไลน์จริง:** migration ยังไม่ได้รันกับ Supabase ใด ๆ, หน้า `multiplayer.html` ยังเป็นข้อมูลจำลอง, ไม่มีกระจายโจทย์ การส่งคำตอบ คิดคะแนน หรือ Ranking จริง และยังไม่มีการสมัครบัญชีที่เชื่อมกับ UI หรือ Realtime listener

## ก่อนเปิดใช้งาน

1. สร้างโปรเจกต์ Supabase สำหรับ **ทดสอบ** แยกจาก production
2. เปิด **Anonymous sign-ins** ใน Authentication ตามคู่มือ Supabase และเปิด CAPTCHA / abuse protection ก่อนเปิดสาธารณะ
3. ตรวจ SQL migration ทุกบรรทัด แล้วใช้ SQL Editor หรือ Supabase CLI รันในโปรเจกต์ทดสอบเท่านั้น
4. ทดสอบด้วยอย่างน้อยสอง anonymous user sessions แยกกันและตรวจ RLS ก่อนเชื่อมเว็บ
5. ห้ามใส่ `service_role` key, database password หรือ secret ลง repository/เว็บ GitHub Pages
6. บนเว็บสาธารณะจะใช้ได้เฉพาะ Supabase URL กับ publishable/anon key ภายใต้ RLS ที่ตรวจแล้ว

## ตัวอย่างเรียก RPC (หลังตั้งค่า Auth แล้ว)

```js
// supabase เป็น client ที่ล็อกอินแบบ anonymous สำเร็จแล้ว
const { data, error } = await supabase.rpc('math24_create_room', {
  p_name: 'ม.5/1', p_question_count: 10, p_duration_minutes: 10,
  p_mode: 'basic', p_difficulty: 'easy', p_ranking_mode: 'final'
});
```

ฟังก์ชันจะคืน `{ok:true, room_id, code}` หรือ `{ok:false, error}`; ต้องตรวจ `ok` เสมอ

## ทดสอบความปลอดภัยก่อนใช้จริง

- ผู้ใช้ A สร้างห้อง / ผู้ใช้ B เข้าด้วยรหัส / ผู้ใช้ C ไม่รู้รหัสและอ่านห้องนั้นไม่ได้
- ไม่ได้ล็อกอินต้องสร้างหรือเข้าห้องไม่ได้
- B กดพร้อมตัวเองได้ แต่กดพร้อมแทน A ไม่ได้
- B เริ่มห้องไม่ได้; เจ้าของเริ่มได้เมื่อมีผู้เล่นอย่างน้อย 2 คนและทุกคนพร้อม
- ห้ามแก้ไข `rooms`, `room_members`, `join_limits` ตรงจาก browser
- ลองรหัสผิดเกิน 5 ครั้งถูกจำกัด 10 นาที (นับต่อบัญชี)
- สมาชิกในห้องต้องไม่อ่านห้องอื่นหรือรายชื่อผู้เล่นห้องอื่นได้
- ห้องเต็ม 50 คนและรหัสหมดอายุจะไม่รับสมาชิกเพิ่ม
- ตรวจการแย่งเข้า/ออกห้องพร้อมกัน และการสร้างห้องซ้ำของเจ้าของห้อง
- ยังต้องทดสอบการใช้งานพร้อมกันจริง, การ reconnect, RLS และ query plan

## ความเสี่ยงที่ยังต้องแก้ก่อนเปิดให้ผู้เล่นจริงใช้

- **รหัส 6 หลักไม่ใช่รหัสผ่าน** แม้มี rate limit ต่อบัญชี ผู้โจมตีอาจสร้างบัญชี anonymous ใหม่ได้เรื่อย ๆ ต้องมี CAPTCHA/IP-level หรือ Edge Function rate limiting เพิ่ม
- ผู้สร้างห้องเรียกว่า “ครู/เจ้าของห้อง” ใน UI แต่ anonymous account ยัง **ยืนยันไม่ได้ว่าเป็นครูจริง** หากจำเป็นต้องยืนยันตัวครู ต้องเพิ่ม Auth ของผู้ดูแล/ครู
- RPC `math24_start_room` เปลี่ยนสถานะห้องเท่านั้น **ยังไม่เริ่มรอบแข่งขันจริง** ห้ามนำคะแนนที่ browser คิดเองไปเป็น Ranking จริง
- ยังไม่มีการเก็บหรือสุ่มโจทย์ฝั่ง server, server-authoritative deadline, ตรวจคำตอบ/คะแนนฝั่ง server, หรือ anti-cheat
- ยังไม่มี realtime. แนะนำใช้ Supabase Broadcast แบบ private สำหรับงานที่มีผู้เล่นจำนวนมาก; ใช้ Postgres Changes ในระยะทดลองได้หลังตรวจ RLS
- ยังไม่มี migration rollback หรือระบบ cleanup ห้องหมดอายุ; ต้องวางแผนก่อน production
- migration และ SQL ยังไม่ได้ทดสอบกับฐานข้อมูล Supabase จริง เพราะไม่มีโปรเจกต์หรือ credentials เชื่อมเข้ามา

## ลำดับพัฒนาถัดไป

1. ทดสอบ migration + สิทธิ์ RLS บน Supabase โปรเจกต์ทดสอบให้ผ่าน
2. เชื่อม `multiplayer.js` กับ Anonymous Auth, RPC และห้องรอสด (ยังเก็บหน้า demo ไว้)
3. ย้ายสุ่มโจทย์, ตรวจคำตอบ, นาฬิกาและคะแนนไปเป็น server authoritative ก่อนเปิดแข่งขันจริง
4. ทำระบบผลการแข่งขันและ Ranking พร้อมทดสอบผู้เล่นหลายเครื่อง
